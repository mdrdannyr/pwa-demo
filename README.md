# PWA Demo - Task Collaboration with GDrive

A tiny installable, offline-capable Progressive Web App: a to-do list that can sync its state to the signed-in user's own Google Drive and be shared for co-working. The GitHub repository is [`mdrdannyr/pwa-demo-task-collaboration-with-gdrive`](https://github.com/mdrdannyr/pwa-demo-task-collaboration-with-gdrive).

## Features

- Web app manifest (installable, standalone display)
- Service worker that pre-caches the app shell and works offline
- Responsive layout: sidebar on desktop; on phones, user/connection/cog in a top bar and Tasks in a bottom bar, with fluid spacing and touch-sized controls
- Online/offline indicator and automatic PWA install support from the browser
- Light and dark themes
- Login gate: Tasks and Settings are only available after signing in
- Combined "Sign in & connect Drive" (account chooser, profile and Drive permission in one popup)
- Generic Google Drive-backed app-state sync with field-level merge
- In-app email invites for collaborators and a Drive Picker flow for opening shared files

## Run locally

Service workers need http://localhost or HTTPS:

    python3 -m http.server 8000

Then open http://localhost:8000.

## Icons

The PNG icons are generated by `python3 tools/make_icons.py` (standard library only).

## Google setup

1. In Google Cloud Console, enable the **Google Drive API**.
2. Create an **OAuth client ID** (Web application) in `APIs & Services -> Credentials`.
3. Add authorized JavaScript origins (origin only, no path/trailing slash):
   - `https://mdrdannyr.github.io`
   - `http://localhost:8000` (and `http://localhost` for local testing)
4. Put the client ID in `config.js` as `googleClientId`. It is public, not a secret.
5. Create an **API key**, restrict it to your HTTP referrers and to the Google Picker API, and put it in `config.js` as `googleDriveApiKey`. The Picker is needed so another user can open a file shared with them while the app uses the narrow `drive.file` scope.
6. The app requests `openid email profile` plus `drive.file` in one Google popup. The profile comes from Google's userinfo endpoint and is used only for display; Google Drive permissions are the actual access control. This is a client-side demo with no backend, so it is not secure authentication for a production app.

When you change any app file, bump `APP_CACHE_VERSION` in `version.js` so returning visitors get the update.

## Login page

When nobody is signed in, the app shows a single **Sign in to continue** page and hides the sidebar, Tasks, and Settings. The sign-in button also connects Drive in the same popup. Visiting `#tasks` or `#settings` while signed out shows the login page; signing in moves on to Tasks. Sign out is in **Settings → Account & Drive** and returns to the login page.

## Settings page

The sidebar has **Tasks** and **Settings** pages. The signed-in user's avatar and name appear at the bottom of the sidebar, with **My Drive** or **Shared file** shown next to the name so it is clear where changes are being written. Settings contains three sections:

1. **Account & Drive** — sync status, the data file's **actual** Drive location, a link to open it in Drive, the last sync time, a reconnect control when needed, and Sign out. The commit SHA the app was built from appears at the bottom of the page.
2. **Share your file with others** — explanation and email invite form for giving collaborators editor access to your data file.
3. **Open a file shared with you** — explanation and the "Open shared file" button for loading someone else's shared data file.

You can link directly to it with `#settings`.

The version shown at the bottom comes from `version.js`: the commit SHA is stamped with `tools/stamp-version.sh`, and the `v` number is the service-worker cache version shared with `sw.js`. Bump `APP_CACHE_VERSION` in `version.js` when app files change so devices pick up the new build.

## Drive sync and sharing

- **Sign in & connect Drive** is a single click: Google shows the account chooser and consent once, the app reads the profile, and it immediately creates (or finds) a `PWA Demo` folder with a `data.json` file in the user's My Drive, then uploads the current local state. Existing tasks from the old localStorage-only version are merged in, not discarded.
- Installs that used the old top-level `PWA Demo state.json` are migrated automatically: the same file is moved into the folder and renamed, keeping its id and sharing permissions.
- On later visits, access renews silently. The **Connect Drive** button only appears when Google needs you to authorize again (or an auth error occurs); transient offline/Drive errors do not ask you to reconnect. Clicking it also tries a silent renewal first and only opens the consent popup when Google no longer has a usable session. The popup must be opened from a click; browser popup blockers reject background attempts with `popup_failed_to_open`.
- Local edits are saved in localStorage immediately, then pushed to Drive (debounced). If the device is offline, edits queue up locally and sync when it comes back.
- The app polls Drive every 60 seconds for changes made by collaborators, and shows the last successful sync time on the Settings page. If the saved data file is deleted or moved to Trash, the next sync creates a fresh `PWA Demo/data.json` from the local state instead of reporting success against a hidden file.
- The owner can invite collaborators with **Share**; they get writer access to the Drive file.
- A collaborator chooses **Open shared file** once to pick that JSON file in Drive. With the `drive.file` scope, an app can only access files it created or that the user explicitly picked — sharing alone does not grant the app access.
- Sharing is done through real Google Drive permissions: the file lives in the owner's Drive, and collaborators edit the file in their own Google accounts.

## Generic state layer (`sync.js`)

`sync.js` is app-agnostic. It stores one JSON document in Drive:

```json
{
  "format": "app-state-v1",
  "clock": 12,
  "values": {
    "theme": { "value": "dark", "rev": { "t": 4, "by": "actor-id" } }
  },
  "collections": {
    "tasks": {
      "task-id": {
        "text": { "value": "Buy milk", "rev": { "t": 7, "by": "actor-id" } },
        "done": { "value": false, "rev": { "t": 8, "by": "actor-id" } },
        "deleted": { "value": false, "rev": { "t": 2, "by": "actor-id" } }
      }
    }
  }
}
```

Every field is a last-write-wins register ordered by a Lamport clock and a random actor id. Merging never overwrites an entire file: two people editing different tasks (or different fields of the same task) both keep their changes. Deletes are tombstones so they propagate.

Any app can use it through `window.AppSync`:

| Method | Purpose |
| --- | --- |
| `onChange(fn)` / `onStatus(fn)` | Subscribe to state / sync status |
| `state()` | Plain `{ values, collections }` snapshot |
| `list(collection)` / `get(collection, id)` | Read records |
| `upsert(collection, id, patch)` / `remove(collection, id)` | Edit records |
| `set(key, value)` | Store a top-level value |
| `connect()` | Request Drive access from a user click, then link the data file |
| `syncNow()` | Pull and push immediately |
| `openPicker()` | Open an existing (shared) data file |
| `share(email, role)` | Invite a collaborator (`reader`, `commenter`, `writer`) |

`app.js` is now a thin consumer: its task list is just the `tasks` collection.

## Limitations

- Merge is per field, last-write-wins: simultaneous edits to the *same* field still have one winner. It is not an operational-transform/CRDT text editor.
- Polling every 60 seconds means collaborator changes can take up to a minute to appear.
- Tokens are kept in memory and requested with the narrow `drive.file` scope; no token or refresh token is stored.
- The state is plain JSON in the user's Drive. It is not encrypted by the app; Drive's own access controls apply.
